## Commands

```bash
# Install deps (preferred)
uv sync

# Configure
cp .env.example .env   # fill in credentials — see comments in .env.example
# NCBI_CONTACT_EMAIL is required (NCBI usage policy); NCBI_API_KEY is optional
# (raises the E-utilities rate limit from 3 req/s to 10 req/s)

# Start Postgres (conversation checkpoints + sessions list) — must be up before the backend
docker compose up -d postgres

# Run the backend — no ingestion step needed, retrieval is live against PubMed
uv run uvicorn app.main:app --reload

# Run the chat UI (separate terminal)
uv run streamlit run streamlit_app.py

# Run the eval suite UI (backend must be running on :8000)
uv run streamlit run evals/app.py
```

Unit + integration tests live in `tests/` (`uv run pytest`); they mock the LLM/PubMed/Jina calls and need a running Postgres (`docker compose up -d postgres`) for the checkpointer. End-to-end answer quality is checked separately via the eval suite (`evals/`), which drives the live `/query` endpoint against `evals/golden_dataset.json` and scores with RAGAS/DeepEval.

## Architecture

Request flow: `Streamlit UI` → `FastAPI /query` → `NeMo Guardrails gate` → `LangGraph agent` → response.

- **Guardrails gate first** (`app/guardrails/rails.py`, rules in `colang_rules.py`): every query hits this before the agent. If a rail fires, `main.py` returns the guardrail's response immediately and the LangGraph agent never runs. Uses a small/fast Groq model (`allam-2-7b`) for intent classification, distinct from the main RAG model. Layers: a regex-based PII check (`app/guardrails/pii.py` — email/phone/SSN/credit-card patterns, checked in plain Python before the NeMo call; deliberately not an NLP/NER model like Presidio+spaCy, which needs a large model resident in memory per request), few-shot dialog rails (off-topic/jailbreak/greeting/farewell/capabilities), and a `self check input` LLM policy check (catches jailbreak paraphrases the few-shot examples miss). This is an **input-only** gate — the LangGraph-generated answer is never routed back through NeMo, so there's no equivalent output rail.
- **Input validation & rate limiting** (`app/main.py`): `QueryRequest.q`/`thread_id` are length-bounded via Pydantic `Field` constraints (`settings.MAX_QUERY_CHARS`/`MAX_THREAD_ID_CHARS`), rejecting empty/whitespace-only or oversized input with a 422 before the guardrails gate even runs. `POST /query` is rate-limited per client IP via `slowapi` (`settings.RATE_LIMIT_QUERY`). Conversation history inlined into planner/responder prompts is capped to `settings.MAX_HISTORY_CHARS` via the shared `app/agents/history.format_history()` helper (drops oldest turns first) so prompt size stays bounded regardless of conversation length.
- **LangGraph agent** (`app/agents/graph.py`): an 8-node graph — `planner` → (conditionally) `retriever` → `evidence_extractor` → `evidence_validator` → (conditionally) `responder` → (conditionally) `claim_verifier` → END, with two bounded cycles (`query_rewriter → retriever` and `claim_verifier → responder`) and a `web_search` fallback arm. Compiled with `PostgresSaver` checkpointed by `thread_id` for per-conversation memory (`settings.DATABASE_URL`) — durable across backend restarts, unlike the old in-memory `MemorySaver`. State shape is `AgentState` (`app/agents/state.py`). The design rationale is `DOCS/arch-feedback.md`: evidence extraction and sufficiency-checking are separate bounded responsibilities, and every retry/fallback is an explicit graph edge rather than logic hidden inside a node.
  - `planner` (`nodes/planner.py`) reads the full conversation history and, via structured output (`.with_structured_output()`), classifies the latest message as `CONVERSATIONAL` (routes straight to responder, uses memory only) or `CLINICAL` — extracting a rewritten PubMed search query, optional date-range/publication-type filters, and whether the user is asking for a fresh search (`fresh_search_requested`, e.g. "search more"/"try again").
  - `retriever` (`nodes/retriever.py`) does **one** retrieval pass per invocation. It decides between a live PubMed search and this thread's cached results: a fresh live search runs on the first message of a conversation, when the UI's "PubMed Search" toggle is on, when the planner detected `fresh_search_requested`, or when it's on a `query_rewriter → retriever` cycle (`retrieval_attempts > 0`); otherwise it queries the thread-scoped session cache first and only falls through to a live search if that cache is empty or below a relevance threshold (`SESSION_CACHE_RELEVANCE_THRESHOLD`). A live search calls NCBI E-utilities (`services/retrieval/pubmed_service.py`: ESearch → batched EFetch), then reranks title+abstract against the query via Jina's hosted reranker API (`services/retrieval/ranking_service.py`, `JINA_RERANK_MODEL`) and publishes the top score as `rerank_top_score` for the validator (there is no in-node CRAG loop any more). Of the reranked results, the top `FULLTEXT_TOP_N` get open-access full text fetched from NCBI's BioC-PMC API (`services/retrieval/bioc_service.py`) and built into markdown (`services/retrieval/markdown_builder.py`); the rest stay abstract-only. Keeps the top `PUBMED_STORE_TOP_N` for the session cache and the top `EVIDENCE_TOP_N` for this turn.
  - `evidence_extractor` (`nodes/evidence_extractor.py`) turns retrieved PubMed abstracts into structured, PMID-grounded `Evidence` records (`EvidenceRecord`/`EvidenceExtraction` Pydantic models) via structured output — any record citing a PMID outside the retrieved set is dropped as a hallucination guard. Emits `evidence: []` when nothing usable comes back; it no longer makes the "insufficient" control-flow decision itself.
  - `evidence_validator` (`nodes/evidence_validator.py`) is a claim-level sufficiency check: one structured-output call returning `EvidenceValidation` — `sufficient`, a typed `reason` (`sufficient` / `query_failure` / `population_mismatch` / `corpus_failure`), per-axis `coverage` (`intervention`/`population`/`outcome`), and `notes`. It writes `evidence_verdict` and decides nothing; `route_validator` in `graph.py` turns the verdict into a route: sufficient (or a direct-PMID turn) → `responder`; `query_failure`/`population_mismatch` with retry budget left (`retrieval_attempts < CRAG_MAX_RETRIES`) → `query_rewriter`; `corpus_failure`, or retry budget spent → `web_search`.
  - `query_rewriter` (`nodes/query_rewriter.py`) is the other arm of the `retriever ⇄ query_rewriter` cycle: a small LLM call (`QueryRewrite`) rewrites `current_query` using the validator's `notes`, bumps `retrieval_attempts`, and edges back to `retriever`.
  - `web_search` (`nodes/web_search.py`) is the `corpus_failure` fallback — a Tavily search (`app/services/websearch/tavily_service.py`, `TAVILY_API_KEY`, optional) whose hits go to the responder to answer **with an explicit "outside the curated PubMed evidence base" disclaimer + source links**. Missing key / failed call → `web_results: []` and the responder emits the insufficient-evidence message. `used_web_fallback` steers the responder and is surfaced by `main.py` as `web_sources`.
  - `responder` (`nodes/responder.py`) generates the answer in one of four modes — conversation memory, web fallback (disclaimer + links), an "insufficient evidence" message, or evidence-grounded prose citing PMIDs — and derives the `citations` list deterministically from `evidence` + `documents`. For grounded answers it does **not** append the assistant message (the `claim_verifier` does, once, so the regenerate cycle can't leave duplicate turns); every other mode is terminal and appends here. `route_responder` sends grounded answers to `claim_verifier`, everything else to END.
  - `claim_verifier` (`nodes/claim_verifier.py`) fact-checks the grounded draft against its evidence (`CritiqueResult`). All claims supported → append the answer, END. Unsupported claims with retry budget left (`verify_attempts < CLAIM_VERIFY_MAX_RETRIES`) → flag them and loop back to `responder`, which regenerates with a directive to drop them. Budget spent → append the visible `### ⚠️ Self-Check Note` caveat and END. (This is the self-critique that used to live inline in the responder.)
  - After the graph returns, `main.py` schedules a `BackgroundTasks` job to embed and upsert this turn's live PubMed results into the session cache (Qdrant, filtered by `thread_id`) — the response is sent before that storage completes.
- **LLM gateway** (`app/gateway/client.py`): all agent nodes get their LLM via `get_langchain_llm()`, which returns a `ChatOpenAI` pointed at Portkey's OpenAI-compatible gateway (`PORTKEY_GATEWAY_URL`) rather than `ChatGroq` directly — this is what gives fallback (primary → fallback virtual key), caching, and retry across the whole agent. Do not swap this for a direct `ChatGroq` call in agent nodes; that would bypass the gateway's fallback/cache/retry behavior. Portkey is configured as a saved server-side Config (`settings.PORTKEY_CONFIG`) because this org has `block_inline_config` enabled — inline strategy/cache/retry/target dicts passed from code are rejected, so gateway behavior changes must be made in the Portkey dashboard, not in `client.py`.
- **PubMed retrieval** (`app/services/retrieval/pubmed_service.py`): live NCBI E-utilities client (ESearch + batched EFetch, `xml.etree.ElementTree` parsing, throttled to NCBI's rate limits). There is no static ingestion pipeline or pre-populated corpus — every clinical answer is grounded in literature fetched at query time or reused from this thread's session cache.
- **Session cache** (`app/services/retrieval/qdrant_service.py`): Qdrant repurposed as a per-thread cache of live PubMed results (not a static admin-curated corpus) — one shared collection (`pubmed_session_cache`) filtered by a `thread_id` payload field. Each document's markdown (abstract + any fetched full text) is header-aware split into chunks (`app/ingestion/chunking.py`, `CHUNK_SIZE`/`CHUNK_OVERLAP`) and stored one Qdrant point per chunk; `query_session_cache()` searches chunks then regroups the highest-scoring ones back into one result per PMID. `app/services/retrieval/embedding.py` embeds via Jina's hosted embeddings API (`JINA_EMBEDDINGS_MODEL`, `retrieval.passage`/`retrieval.query` tasks) — there is no local embedding model.
- **Sessions list** (`app/services/sessions_service.py`): a small `sessions` table in the same Postgres instance (thread_id, title, created_at, updated_at) — separate from the LangGraph checkpoint tables, purely so the UI can list/switch threads without scanning checkpoints. `main.py` upserts a row on every `/query`/`/query/stream` call (title = first message, truncated); `GET /sessions` lists them by recency and `GET /sessions/{thread_id}/history` replays a thread's messages from the checkpointer for the Streamlit sidebar (`streamlit_app.py`) to rehydrate on switch. Replayed history only has role/content — citations and thought-process are computed per-turn and not persisted per message.
- **Config** (`app/config.py`): a single `Settings` class reads all env vars (Qdrant, Postgres, NCBI/PubMed, Groq, Jina, Portkey, LangSmith) via `dotenv`; import `settings` from here rather than reading `os.getenv` directly elsewhere. Secrets (`NCBI_API_KEY`, `NCBI_CONTACT_EMAIL`, `JINA_API_KEY`, `DATABASE_URL`, etc.) are read from `.env` only — never hardcode a default for anything secret.
- **Observability**: `app/main.py` configures `logfire` before any other import (module-level ordering matters — it must capture spans from everything imported after it) so its `logfire.configure()` call must stay the first statement in any new entrypoint. LangSmith tracing is enabled globally via env vars set at the bottom of `app/config.py`.
- **Evals** (`evals/`): `pipeline.py` replays `golden_dataset.json` against the live `/query` endpoint (`app.py` is the Streamlit driver), `guardrails_eval.py` scores the guardrails gate separately, and `metrics.py` runs RAGAS/DeepEval scoring on the captured results. Since retrieval is now live, eval runs make real NCBI calls per clinical sample in addition to Groq calls — set `NCBI_API_KEY` in the eval environment to stay comfortably within NCBI's rate limit.
